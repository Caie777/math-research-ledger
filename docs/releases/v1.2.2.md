# MathResearch Ledger 1.2.2

Prepared 2026-10-26. Support-policy clarification added 2026-10-30; historical
acceptance below retains its original date and Host versions and is not a new run.
This release closes two practical gaps: registering a new research Problem through
MCP, and carrying one installation between research workspaces without pinning a
research directory into the default deployment.

## Protocol-neutral, DSH-first support

DSH is **Tier 1 official**: actively developed, documented and regression-tested;
Core + MCP + actual DSH Host acceptance form the release-blocking gate.
Codex is **Tier 2 compatibility**, retained best-effort without dedicated Harness
regression for every feature. Codex-only issues are normally non-blocking unless
shared Core/MCP semantics are affected. Other Harnesses are **Tier 3 on demand**:
no dedicated adapter until a real use case. The standard MCP contract and shared
services remain Harness-neutral. See [development gates](../development.md).

## Explicit Problems, shared memory

Real research use exposed the missing formal Problem create/update interface.
`research_create_problem` and `research_update_problem` bring the MCP surface to
eleven tools. Both support preview. Metadata and active/paused/closed lifecycle
changes stay distinct from explicit semantic revisions of a statement or target.
Closing a Problem does not verify a theorem or grant human acceptance.

Workspace state belongs to the user's workspace. The DSH default package selects a
Python runtime, while trusted session context selects the research root; installation
must still be performed and the package selected in the intended Profile. Core
remains Harness-independent: DSH and Codex use the same Python services, MCP schemas,
error codes, authority gates, Episode/checkpoint semantics and shared research
workflow, with thin adapters for their Host lifecycles.

## DSH default, Codex compatibility

DSH's [Agent Host plugin](../../integrations/deepseek-harness/host-plugin/README.md)
is the default installation path. It mounts the official MCP client inside each
Agent's scope using its persisted session header. The old config-only Bundle is
**manual / single-workspace fallback only**. The two DSH deployments are mutually
exclusive in one Profile.

For users who need Codex, its native compatibility plugin owns the shared Skill and
bundled MCP together. Startup cwd comes from the Host session; project-level direct
MCP is a legacy fallback, not the default product installation path.

Exact-root binding prevents a session started in a subdirectory or the state
directory from silently reading a parent's research. `--workspace .` resolves once
at startup. Missing state returns `NO_WORKSPACE`, with no auto-init or fallback.
The tool `workspace` argument only asserts the existing binding.

## Upgrade deliberately

Install the 1.2.2 wheel with `[mcp]` into the chosen persistent Python runtime;
updating source or a plugin alone does not update an installed runtime. Stop its
sessions before replacing it, refresh prepared local packages through normal Host
installation, and start fresh sessions/restart. Check eleven tools and the reported
root before writing. Do not enable a second direct MCP beside the bundled one.
This preparation does not upgrade the user's existing deployments automatically.
The 2026-10-30 Profile audit found both DSH packages installed as dependencies but
neither selected in `bundles`; the historical cutover below does not establish an
enabled current deployment. See the [dated capability matrix](../harness-capability-matrix.md).

See the default [DSH installation](../../integrations/deepseek-harness/host-plugin/README.md),

the [adapter contract](../adapter-contract.md) and

## Validation boundaries

Historical 2026-10-26 Windows DSH 0.2.1-rc.3 and Codex 0.160.0 evidence includes
isolated native Host acceptance and controlled real-workspace/Profile cutovers with
zero Ledger state writes. Those cutovers used native policy/Host APIs, not GUI
conversational turns; they are not a fresh release-gate result. DSH OFF affects
new Agents; existing ones retain clients until disposal. Codex may retain idle
processes after OFF. These lifecycle differences are intentional Host behavior.

Codex's inherited session cwd is measured behavior, not a guaranteed official
`${PROJECT_ROOT}` API. DSH rc.2 is unverified for the Host adapter. macOS/Linux Host
behavior, UNC/network roots, GUI conversational acceptance and real-corpus mutation
acceptance remain unverified. No new Agent loop, model routing, permissions repair,
automatic canonicalization or human-acceptance mechanism is introduced.
